# План маркетингового лендинга ai-message

Документ описывает план, как мы делаем публичный сайт под продукт. Цель —
не разработка, а продажа: посетитель должен за 30 секунд понять, что мы
делаем, поверить и нажать «подключить». Продуктовое приложение (Inbox,
Dashboard) живёт под тем же доменом, на префиксе `/app`.

## Решения, уже принятые

| Вопрос | Решение |
|---|---|
| Тип сайта | Одностраничный маркетинговый лендинг |
| Размещение | Тот же домен, что и приложение: `/` — лендинг, `/app` — продукт |
| Контент | Хардкод в исходниках (без CMS), правки через PR |
| Стек | React + Vite + Tailwind (тот же, что `apps/web`) — нет нового рантайма |
| Хостинг | Внутри существующего nginx-контейнера (общий сертификат, один деплой) |

Решения «потом» (не делаем сейчас):
- Блог/документация — оставляем в `docs/` в репо, public-версия не нужна до старта продаж.
- Локализация EN — Bitrix24-аудитория русскоязычная, переводим когда выйдем за пределы РФ.
- Headless CMS — если правок будет редко, не нужен; если контент-менеджер выйдет на полную ставку, вернёмся.

## Архитектура размещения

Текущее состояние: nginx в `apps/web/nginx.conf` сейчас отдаёт SPA-приложение
на `/` через try_files SPA-fallback. После релиза лендинга меняем разметку:

```
/                       — лендинг (статика, отдельный bundle)
/app, /app/*            — текущий SPA (Inbox, Dashboard, Integrations, Settings)
/install/, /api/, /webhooks/  — без изменений (backend)
```

Это требует:
1. **Перенести SPA-роутер с `/` на `/app`.** В `apps/web/src` сейчас
   `BrowserRouter` без `basename`. Меняем на `basename="/app"` плюс
   правим все ссылки. Это сделать раньше, чем выкатывать лендинг,
   чтобы пути не конфликтовали.
2. **Новый пакет `apps/marketing`** (Vite, без React Router — статика).
   Билд кладёт `dist/` в `/usr/share/nginx/html/` (корень), а SPA-билд
   из `apps/web/dist` — в `/usr/share/nginx/html/app/`.
3. **nginx**: явные `location = /` и `location /app/`. SPA-fallback
   действует только внутри `/app/`. Корневой `index.html` — лендинг,
   не SPA.

Альтернатива «лендинг и SPA в одном бандле» рассмотрена и отклонена:
ради 200 КБ маркетингового контента не хочется тянуть весь React Router
+ TanStack Query + Recharts в первый paint. SEO-краулерам отдаём чистую
статику.

## Структура лендинга (секции)

1. **Hero**
   - Заголовок: «Аналитика всех ваших чатов в одном окне»
   - Подзаголовок: «WhatsApp, Telegram, ВК, Авито и виджет сайта из Bitrix24 — SLA, тональность и AI-инсайты»
   - CTA: «Подключить Bitrix24 за 5 минут» → `/app/integrations/bitrix24/new`
   - Скриншот дашборда (или короткое видео-loop)

2. **Боли и решения** (3 колонки)
   - «Не видно общую картину» → один дашборд по всем каналам
   - «Менеджер пропустил клиента» → SLA-нарушения подсвечены
   - «Не понятно, о чём пишут чаще всего» → AI-темы и тональность

3. **Как работает** (3 шага)
   - Ставите наше приложение в Bitrix24 Marketplace
   - Возвращаетесь в наш кабинет, вводите домен
   - Получаете дашборд и Inbox через 5 минут (с историей за 30 дней)

4. **Скриншоты продукта** (карусель или сетка)
   - Dashboard Overview, Managers, Heatmap, Funnel
   - Inbox со списком диалогов
   - AI-таб (с пометкой «скоро»)

5. **Возможности** (сетка иконок)
   - 8 KPI на дашборде, дельты к прошлому периоду
   - Heatmap день × час
   - Воронка CRM по сделкам
   - SLA-таргеты с подсветкой нарушений
   - Полнотекстовый поиск по сообщениям
   - Экспорт CSV
   - Реальное время через Open Channels
   - AI-инсайты (скоро)

6. **Цены** (упрощённо до первой продажи)
   - Стартовый: до X порталов, бесплатно в beta
   - Pro: цена/мес — заглушка «свяжитесь с нами» до утверждения
   - Enterprise: on-prem, SSO — по запросу

7. **FAQ**
   - Чем отличаемся от стандартных отчётов Bitrix24?
   - Где хранятся данные? (РФ, шифрование Fernet — теперь это правда)
   - Что с GDPR / 152-ФЗ?
   - Можно ли локально (self-hosted)?
   - Какие каналы поддерживаются?

8. **Финальный CTA**
   - «Начать бесплатно» → регистрация в `/app/register`
   - Контакт продаж: email/Telegram

9. **Footer**
   - Юр.лицо, реквизиты-заглушка, политика обработки данных
   - Ссылка на оферту (отдельная страница `/legal/offer`)
   - Ссылки на соцсети (если есть)

## Дизайн-направление

- **Стиль:** минимализм, плотные карточки, скриншоты с реальными данными
  (а не «лорем»), один акцентный цвет, нейтральный фон. Уйти от типовой
  «AI-эстетики» (фиолетовые градиенты на чёрном).
- **Шрифты:** системный стек + Inter для заголовков (через Tailwind),
  никаких внешних CDN — CSP запрещает.
- **Адаптивность:** mobile-first, breakpoint sm/md/lg, hero корректно
  схлопывается в столбик.
- **Анимации:** скупо — fade-in для секций при скролле через
  `IntersectionObserver`, без библиотек. Никаких parallax/heavy webgl.
- **Иконки:** lucide-react (уже в SPA), та же палитра.
- **Скриншоты:** делать в Inbox/Dashboard на специально засеянных тестовых
  данных, чтобы не показывать реальные диалоги. Хранить как `.webp`
  в `apps/marketing/public/screens/`.

## SEO и open graph

- `<title>` + `<meta description>` — захардкожены в `index.html`.
- Open Graph (og:title, og:description, og:image) — для превью в соцсетях.
- `robots.txt` — Allow: /, Disallow: /api/, /webhooks/, /install/, /app/auth/
- `sitemap.xml` — статика, одна запись `/`. Сгенерируем руками.
- Schema.org JSON-LD `SoftwareApplication` для богатой выдачи Google.
- Performance: один HTML + один CSS + один JS бандл < 80 КБ gz без скриншотов.
  Скриншоты — `.webp`, lazy load с `loading="lazy"`.

## Аналитика и метрики

Не подключаем сторонние трекеры (Google Analytics / Яндекс.Метрика)
сразу — каждый трекер ломает CSP и трогает приватность. План:
- Считаем серверные метрики через nginx access-log (DAU посещений `/`).
- Если станет нужно — добавим Plausible (self-hosted, единственный
  скрипт, легко добавить в CSP `script-src`).

CTA-конверсию меряем по факту регистраций в `/app/register` —
это уже видно из БД.

## Юридическое (минимум для запуска)

- Политика обработки персональных данных — `/legal/privacy`,
  отдельная статичная страница. Можно начать с шаблона на основе
  152-ФЗ + GDPR.
- Публичная оферта — `/legal/offer`. До запуска платных тарифов
  можно ограничиться «бесплатная beta».
- Cookie-banner — нужен только если включим внешние трекеры.
  Сейчас не нужен.
- Контакты юр.лица в футере — обязательно, иначе платёжки не
  пропустят при выходе на коммерческий запуск.

## Зависимости от других задач

- **Email verification** (P0 фазы 5) — нужен до открытия `/app/register`
  под публичный трафик, иначе занять чужой email тривиально.
- **TLS** (фаза 7) — обязательно до публичного запуска. Caddy/traefik
  перед nginx, Let's Encrypt.
- **Sentry FE** (фаза 7) — желательно до пуска, чтобы ловить JS-ошибки
  на лендинге у реальных пользователей.

Эти три пункта блокируют не разработку сайта, а его публичный релиз.
